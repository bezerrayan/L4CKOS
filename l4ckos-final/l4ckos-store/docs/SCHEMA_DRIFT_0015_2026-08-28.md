# Correção do schema drift bloqueante — migration 0015

Data da validação: 2026-08-28. Escopo: somente bancos MySQL locais e descartáveis. Nenhuma migration remota, alteração de produção, chamada ao Asaas ou deploy foi realizada.

## A. Drift encontrado

| Tabela | Campo | Schema Drizzle desejado | Migrations 0000–0014 / banco reconstruído | Quem usa |
|---|---|---|---|---|
| `productImages` | `color` | `varchar(60) NULL`, sem default | ausente | leitura em `getProductByIdWithDetails`; escrita em `replaceProductImages`; seleção/fallback por cor no produto e no admin |
| `promoBanners` | `imageUrl` | `varchar(500) NULL`, sem default | ausente | imagem desktop do banner; ausência é válida |
| `promoBanners` | `mobileImageUrl` | `varchar(500) NULL`, sem default | ausente | imagem mobile; fallback para `imageUrl` |
| `promoBanners` | `imageAlt` | `varchar(255) NULL`, sem default | ausente | texto alternativo; fallback para título/texto padrão |
| `promoBanners` | `linkUrl` | `varchar(500) NULL`, sem default | ausente | destino do CTA; fallback para `/produtos` |
| `waitlist_emails` | `created_at` | `timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP` | `timestamp NULL DEFAULT CURRENT_TIMESTAMP` | insert da waitlist omite o campo e depende do default; backup/readiness exigem o contrato atual |

`NULL` é semântico para imagens gerais, não associadas a uma cor, e para banners históricos sem mídia/link. Por isso não houve backfill. A base legada representativa tinha uma imagem, um banner e uma inscrição de waitlist; não havia `created_at IS NULL`.

## B. Causa raiz

Os campos de banner entraram no modelo/código em março de 2026 (`imageUrl`, `imageAlt` e `linkUrl` no commit `06d2220`; `mobileImageUrl` no `21e0ed2`) e `productImages.color` entrou no commit `2eb4640`, mas nenhuma migration correspondente foi criada. A migration `0008_blue_signal.sql` criou `created_at` com default, porém sem `NOT NULL`, enquanto o schema Drizzle passou a exigir não nulo. Assim, `schema.ts`, queries atuais e backup evoluíram além do banco reproduzido por `0000`–`0014`.

## C. Migration 0015

Arquivo: `drizzle/0015_schema_drift_alignment.sql`.

1. `ALTER TABLE productImages ADD COLUMN color varchar(60) NULL AFTER imageUrl`: aditivo; mantém imagens antigas com `NULL`.
2. Um `ALTER TABLE promoBanners` adiciona `imageUrl varchar(500)`, `mobileImageUrl varchar(500)`, `imageAlt varchar(255)` e `linkUrl varchar(500)`, todos nullable e sem default: aditivo e sem dados artificiais.
3. `ALTER TABLE waitlist_emails MODIFY COLUMN created_at timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP`: alinha o contrato atual somente depois de preflight zero para timestamps nulos.

`0013` e `0014` não foram alteradas. O `schema.ts` também passou a representar os índices, FKs e CHECKs já existentes fisicamente por causa de `0014`, permitindo comparação completa sem gerar falso drift.

## D. Preflight

O novo `scripts/preflight-schema-drift.sql` é somente leitura e cobre as seis colunas, registros históricos, timestamps nulos e todas as colunas consumidas pelo backup JSON.

No legado pré-0015:

| Verificação | Resultado |
|---|---|
| imagem histórica sem cor | `WARNING`, 1 registro; `NULL` preservado |
| banner histórico sem mídia/link | `WARNING`, 1 registro; `NULL` preservado |
| `waitlist_created_at_nulls` | `OK`, 0 registros |
| seis contratos de coluna | seis `WARNING` de drift esperado; zero `BLOCKER` de dados |
| contrato de colunas do backup | somente as cinco ausências esperadas; nenhuma ausência fora da 0015 |

No pós-0015, os seis contratos ficaram `OK` e nenhuma coluna esperada pelo backup ficou ausente. Em teste negativo isolado, um registro sintético com `created_at NULL` produziu `BLOCKER` com `affected=1`; o MySQL recusou o `NOT NULL` com `ER_INVALID_USE_OF_NULL`. O fixture foi removido da base descartável, sem backfill.

## I. Backup

Antes da correção, a reprodução falhou no primeiro acesso incompatível:

```text
DrizzleQueryError: Failed query: select id, productId, imageUrl, color, alt, order, createdAt from productImages
cause: Unknown column 'color'
```

O erro não foi ocultado. Depois da 0015, o backup automático gerou `auto-backup-2026-08-28T23-37-01-321Z.json`, com 6.961 bytes e 18 coleções, incluindo `productImages`, `promoBanners` e `waitlistEmails` com um registro cada. O payload/restore foi ampliado para abranger banners, waitlist e as tabelas P0/P1. Também foi corrigida a conversão validada de timestamps JSON para `Date` antes de qualquer exclusão no restore; timestamp inválido aborta com `INVALID_BACKUP_TIMESTAMP:<tabela>.<campo>`.
